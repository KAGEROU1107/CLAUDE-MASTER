# Resource pacing
Use measured context percentage, rolling session allowance and weekly allowance independently. Statusline JSON fields may be absent or null; use only fresh same-session observations or explicit user-reported numbers. Never substitute zero. 60% context: reconcile task state; 70%: prepare verified handover; 80%: no new substantial work, save/read back BATON then ask user to /clear and /baton resume. Session allowance 60%: no heavy work; 80%: checkpoint and pause until actual reset. Weekly allowance 85%: essential work only; ask before heavy tasks. Apply all relevant gates, strongest first. At context+allowance threshold save before pausing; never suggest clear as quota reset. Unknown meter: conservative bounded tasks, checkpoint each milestone, request /context or /usage only when useful. Recheck after large reads and before expensive work. Prefer smallest adequate model/effort when available; never switch provider settings without authorization. Label estimates as estimates; compare fixed tasks before/after. Batch safe independent reads, search before opening, cap outputs, lazy-load modules. No infinite retries or research loops. Budgets are defaults user may change. Stop on real rate-limit errors.

## Required pacing tag (V2 retained and refined)
For every planned substantial task/phase, record `TASK | MODEL(actual/recommended) | EFFORT(actual/recommended) | COST S/M/L (estimated or measured with baseline) | FITS_SESSION TRUE/FALSE/UNKNOWN | FITS_WEEK TRUE/FALSE/UNKNOWN | WHEN now/after reset/later | EVIDENCE`. Estimate cost only as a qualitative class until actual observations exist. Do not fabricate a percentage estimate. UNKNOWN is not TRUE; split into bounded lightweight discovery, ask for the missing meter if critical, or defer. FALSE means split or defer. Record reset time only from provider. Compare weekly use with elapsed fraction between verified weekly reset boundaries; when use exceeds elapsed percentage by >10 points, downshift or defer heavy work; if weekly reset boundaries are unknown, omit the comparison. Thresholds remain independent.

## Model and high-thinking gate
Use the smallest adequate available model for routine reads and formatting; a capable mid-tier model with adequate effort for implementation/tests. For initial architecture, difficult root-cause analysis, security review, complex migration, persona/authority design, high-risk integrations and final release audit: require the highest-capability suitable model actually available within the user's approved budget and **high or greater verified reasoning effort** (or a provider-documented equivalent). Check `/model`, `/effort` or installed supported controls; do not claim a switch happened from prompt wording. Explain expected resource impact and request user selection if needed; never silently change persistent model settings or incur extra spend. Prefer early fresh allowance windows. If the gate cannot be met, do safe read-only reconnaissance and checkpoint, label the critical task MODEL_GATE or METER_GATE and wait for a usable authorized configuration; do not certify a lower-capability workaround as a completed critical review. `xhigh`/`max` only when supported and justified; no automatic agent orchestration. Use a one-time session selection when offered. Restore/recommend the ordinary setting for routine work. Official docs: https://code.claude.com/docs/en/model-config .

Record session, weekly and context readings at phase start/end, before M/L work and after substantial tool output. Use the approved statusline/hooks where supported; otherwise manual checks. The deterministic `tools/pacing.py` decision helper consumes already verified readings and estimated headroom, never changes provider settings. Its READY decision is advisory, not an approval; other authority and test gates still apply. If a context and quota gate coexist, BATON is required before pausing.
